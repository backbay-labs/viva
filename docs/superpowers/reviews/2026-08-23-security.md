# Code Review: Cross-cutting security review

| | |
|---|---|
| **Date** | 2026-08-23 |
| **Commit** | 4d5d827 (main) |
| **Scope** | Entire repo, prioritizing: session-token flow end-to-end (apps/web/app/api/viva-session/ + agent/crates/agent-service auth), apps/web library proxy, agent/Dockerfile, Dockerfile.monitor, railway.json, .env.example, .github/workflows/validate.yml, SECURITY.md, docs/data-governance.md, secret handling in scripts/ and both runtimes |
| **Verdict** | sound-with-fixes |
| **Confidence** | High for source/configuration findings; moderate for deployment reachability |

This review covers the security posture of the Viva public release: the HMAC session-token flow from the web mint routes through the agent's WebSocket auth, the library proxy, secret handling in both runtimes, and the Docker/CI supply chain. The core boundaries — token forgery/replay resistance, server-authoritative identity, fail-closed public binds, and the triple-gated live-provider path — were verified against the code and hold as designed. No forgery, replay, injection, or traversal hole was found. What remains is hardening: both runtime containers execute as root, and the agent's per-IP session limiter keys on the attacker-controlled left-most `X-Forwarded-For` entry — a pre-auth control that can be bypassed entirely. The remaining findings are supply-chain and resource-growth robustness items.

## Strengths

- Session-token design is sound end-to-end: HMAC-SHA256 signatures verified with a constant-time comparison (`agent/crates/agent-service/src/config.rs:971` `constant_time_eq`, `SessionTokenClaims::verify`), single-use nonces enforced at the database via a composite PRIMARY KEY + `INSERT ... ON CONFLICT DO NOTHING` (`agent/migrations/0010_voice_session_token_nonces.sql`, `agent/crates/data/src/postgres.rs:654`), and identity binding (user/study-set/session) rechecked against the token on the first WS frame.
- The server is genuinely authoritative over identity: `sanitize_client_session_config` rejects any identity mismatch and clears browser-supplied `source_context`, `active_concepts`, and `client_generation_id` before the brain or store sees them (`agent/crates/agent-service/src/ws.rs:3077-3103`), matching the README/SECURITY.md promise.
- Non-loopback binds fail closed: `ServiceConfig::validate` refuses to start a public bind without a bearer or session-token secret and without `VIVA_VOICE_WS_ALLOWED_ORIGINS` (`agent/crates/agent-service/src/config.rs:173-192`), so the Docker CMD's default `0.0.0.0` bind will not boot unconfigured.
- Live-provider access is triple-gated and secrets are redacted in Debug impls: `live_runtime_selectable` requires the runtime flag plus real keys plus both ZDR confirmations (`agent/crates/agent-adapters/src/cartesia_gemini/mod.rs:221-225`), and the invalid-API-key error path never echoes the key value (`agent/crates/agent-adapters/src/cartesia_gemini/llm.rs:538`).
- A comprehensive redaction-control gate runs on every PR (`scripts/redaction-control.mjs`, wired into `.github/workflows/validate.yml:33-36`), giving real defense against learner content or secrets leaking into logs and evidence artifacts.
- Supply-chain baseline is healthy: reqwest is `default-features = false` with rustls-tls only (`agent/Cargo.toml:30`), no `danger_accept_invalid_certs` anywhere, and security-relevant crates are current (rustls 0.23.40, sqlx 0.8.6, axum 0.8.9, tokio 1.52.3).
- CI is secret-free by design and uses `pull_request` (not `pull_request_target`), so fork PRs cannot exfiltrate secrets; the whole default validate job runs with `VIVA_AGENT_PROVIDER=synthetic` and no provider keys (`.github/workflows/validate.yml:38-60`).

## Findings

### Important

**1. Runtime containers run as root (no USER directive)**

`agent/Dockerfile:18-31`, `Dockerfile.monitor:1-24`

**What**: Neither the agent runtime image (the `debian:bookworm-slim` stage) nor the hosted monitor image (the Playwright base) drops privileges; both execute their CMD as uid 0 (the monitor even installs Bun into `/root/.bun`). The agent is the internet-facing service and binds `0.0.0.0` by default via its CMD.

**Why it matters**: Running the network-exposed voice service as root removes a key isolation layer: any RCE primitive in the process, its dependencies, or the base image executes as root inside the container, and a writable root filesystem makes tampering and lateral movement easier. This is baseline hardening for the project's public-release posture.

**Fix**: Add a dedicated non-root user in each runtime stage (e.g. `RUN useradd -r -u 10001 viva` then `USER viva`), ensure the binary and any writable evidence dir are owned by that uid, and consider a read-only root filesystem at deploy time.

**2. Per-IP session limiter keys on the spoofable left-most X-Forwarded-For entry**

`agent/crates/agent-service/src/ws.rs:189-205`

**What**: `session_ip_key` reads `x-forwarded-for`, splits on comma, and takes `.next()` — the left-most entry, which is the value the original client supplied and is fully attacker-controlled (trusted proxies append the real hop on the right; `x-real-ip` is only consulted when XFF is absent, so a spoofed XFF always wins). An attacker sending a rotating `X-Forwarded-For` on each WebSocket upgrade makes every connection a distinct bucket in `ActiveVoiceLimits`, so the `VIVA_VOICE_WS_MAX_IP_SESSIONS` cap never trips.

**Why it matters**: Verification confirmed this limiter is a pre-authentication control: the IP lease and the global session-slot permit are acquired in the HTTP preflight (`ws.rs:91-123`) before the upgrade, while the session token is only verified on the first WS frame (`ws.rs:288-312`). The per-IP cap is therefore the layer meant to stop an unauthenticated single source from churning connections against the global slot semaphore (each connection holds a slot until the first-frame timeout), and it is bypassable with one spoofed header. The per-user/study-set caps are identity-bound and unaffected, but they only apply after auth. Notably the web tier gets this right — `apps/web/app/api/viva-session/shared.ts:995-1010` `clientIp` prefers trusted platform headers, then the right-most XFF entry — so the agent is the inconsistent side.

**Fix**: Behind a known proxy, take the Nth-from-right XFF entry (or a platform-specific trusted header the edge sets) rather than the left-most value, configurable via env with a documented trusted-hop count, mirroring the web tier's logic.

### Minor

**1. Validate workflow defines no `permissions:` block**

`.github/workflows/validate.yml:10-13`

**What**: The only workflow in the repo sets no top-level or job-level `permissions:` key, so GITHUB_TOKEN gets whatever the repository default grants for every step, including third-party actions (setup-bun, dtolnay/rust-toolchain, upload-artifact).

**Why it matters**: If the repo default is write-scoped, a compromised or repushed action tag could push commits or tags. The exposure is contingent: fork-PR tokens are read-only regardless, GitHub's default token scope for newly created repos has been read-only since 2023, and this CI is secret-free by design — which is why this is minor rather than important. An explicit block is still the correct control because it does not depend on repo settings staying right.

**Fix**: Add `permissions: { contents: read }` at the workflow top level (contents: read suffices for `actions/upload-artifact`).

**2. Base images pinned by moving tag, not by digest**

`agent/Dockerfile:3,18`, `Dockerfile.monitor:1,5`

**What**: `rust:1.94.1-slim-bookworm`, `debian:bookworm-slim`, and `mcr.microsoft.com/playwright:v1.61.0-noble` are mutable tags; `debian:bookworm-slim` in particular changes content over time. Dockerfile.monitor additionally installs Bun via `curl -fsSL https://bun.sh/install | bash` (line 5).

**Why it matters**: Tag-only pins make builds non-reproducible and let an upstream tag repush (or registry compromise) silently change what ships in a security-sensitive service.

**Fix**: Pin each FROM to an immutable `@sha256:` digest and bump via a controlled process; for the Bun install, verify a pinned installer checksum rather than piping the live script to bash.

**3. Third-party GitHub Actions pinned to floating tags, not commit SHAs**

`.github/workflows/validate.yml:16,21,26,64`

**What**: `actions/checkout@v4`, `oven-sh/setup-bun@v2`, `dtolnay/rust-toolchain@1.94.1`, and `actions/upload-artifact@v4` are referenced by mutable tag, which the action owner (or an attacker who compromises the action repo) can repoint.

**Why it matters**: A repushed tag executes attacker-controlled code inside CI with whatever GITHUB_TOKEN permissions the job holds — and combined with the missing permissions block above, that scope is whatever the repo default is. Pinning to a full commit SHA is the recommended supply-chain control.

**Fix**: Pin each third-party action to a full 40-char commit SHA (with a comment noting the version) and use Dependabot's action-pinning updates to bump deliberately.

**4. Session-token nonce rows are never pruned on expiry**

`agent/crates/data/src/postgres.rs:654`

**What**: `claim_session_token_nonce` inserts one row per connecting session token and relies on the composite PK for replay protection. Verified: the only DELETEs against `voice_session_token_nonces` are the explicit privacy deletes (`postgres.rs:1331`, `:1439`); nothing removes rows past `expires_at`, despite the expiry index existing in migration 0010.

**Why it matters**: In a long-lived durable deployment the table grows one row per session ever started, degrading the replay-guard insert/lookup and consuming storage — availability erosion that undercuts the durable-store readiness posture.

**Fix**: Add a periodic prune (`DELETE FROM voice_session_token_nonces WHERE expires_at < $now`) via a scheduled task or opportunistic on-connect cleanup; expired nonces cannot be replayed anyway since the token is already rejected as expired.

**5. In-memory mint rate-limit map accumulates stale keys**

`apps/web/app/api/viva-session/shared.ts:163`

**What**: `mintRateLimits` is a module-level Map keyed by IP and by user/study-set identity. `currentRateLimitBucket` (`:504-508`) replaces an expired bucket for a returning key, but nothing deletes keys for clients that never return — the only `.clear()` is the test helper `resetVivaSessionMintRateLimitsForTests` (`:272`).

**Why it matters**: On short-lived serverless instances impact is limited, but on a long-running Node instance this is an unbounded-growth vector inflatable by varying the observed IP; it is also per-instance state that resets on redeploy and does not coordinate across horizontally scaled instances.

**Fix**: Prune expired buckets on access (delete when `resetAt <= now`) or cap map size with a TTL structure; for correctness under scaling, back the limiter with shared state.

**6. .gitignore misses non-.local dotenv variants**

`.gitignore:10-12`

**What**: The ignore list covers `.env`, `.env.local`, `.env.*.local`, and `agent/.env`, but not `.env.production`, `.env.development`, or similar variants. SECURITY.md states `.env` is gitignored and only `.env.example` carries placeholders.

**Why it matters**: A contributor creating `.env.production` — a natural filename for real deployment secrets — finds it untracked-but-not-ignored, making an accidental `git add .` commit of production session-token secrets or provider keys easy.

**Fix**: Broaden the ignore to `.env*` with an explicit unignore for `!.env.example` (and `!*/.env.example`) so any dotenv variant is ignored by default.

## Verification notes

- F2 (missing workflow `permissions:` block) — downgraded from important to minor. The factual claim holds (no `permissions:` key anywhere under `.github/`), but the impact rests on the repo's default token being write-scoped, which cannot be verified from the checkout and is contrary to GitHub's read-only default for newly created repos; fork-PR tokens are read-only regardless, and the workflow handles no secrets. The fix remains worth doing.
- F1 (root containers) — confirmed against both Dockerfiles: no USER directive in either runtime stage; the monitor image demonstrably runs as root (Bun installed to `/root/.bun`).
- F3 (left-most XFF) — confirmed, and the severity case strengthened: verification established the per-IP lease is acquired at HTTP preflight before any token verification (token checked on the first WS frame), making this a bypassable pre-auth control rather than a post-auth redundancy. The contrasting correct implementation in the web tier was verified at `shared.ts:995-1010`.
- All five original minors (F4-F8) were spot-checked against the cited files and confirmed; the `mintRateLimits.clear()` at `shared.ts:273` was checked and is a test-only helper, not a runtime prune.
- Nothing was refuted.

## Recommendations

- Add non-root USER directives (and consider read-only root filesystems) to both Dockerfiles, and pin base images plus CI actions to immutable digests/SHAs as part of the public-release hardening pass.
- Fix the agent's X-Forwarded-For parsing to read the trusted hop rather than the left-most client-supplied value, mirroring the logic already in the web tier's `clientIp`, and make the trusted-hop count configurable.
- Add a least-privilege `permissions: { contents: read }` block to `.github/workflows/validate.yml` so token scope no longer depends on repository settings.
- Introduce expiry-based pruning for `voice_session_token_nonces` and bounded/TTL behavior for the web mint rate-limit map so both stay bounded in long-running deployments.
- Document (or enforce in code) that production web+agent deployments must set both `VIVA_AGENT_REST_BEARER_TOKEN` and `VIVA_VOICE_SESSION_TOKEN_SECRET`, since the browser delete/export flow silently 503s without the REST bearer.
- Protect the redaction-control gate and the `pull_request` (non-target) CI model with branch rules so these load-bearing controls cannot be removed without review.

## Assessment

**Verdict: sound-with-fixes** (unchanged from the first-pass reviewer; one important finding was downgraded to minor during verification, which does not alter the overall verdict). The security boundaries this audit prioritized — token forgery/replay resistance, server-authoritative identity, fail-closed public binds, the triple-gated live-provider path, and the no-secrets CI posture — were all verified against the code and hold. The two confirmed important items are genuine hardening gaps rather than active breaches: root-running containers and a spoofable pre-auth per-IP limiter, both with straightforward fixes; the remaining items are supply-chain pinning and unbounded-growth robustness. Addressing the two important findings moves this from a solid implementation to a well-hardened one.
