This area is the student-facing surface of Viva: the landing page with its library panel, and the `/session` live oral-exam page — an 800+ line client component orchestrating WebSocket lifecycle, mic capture, audio playback, barge-in, and two animated canvases. The React and canvas engineering is unusually careful, and the accessibility work is genuinely thoughtful. But adversarial verification confirmed every first-pass finding, including one critical cross-layer contract bug: in live-provider mode, a spoken answer longer than about one second serializes into a single JSON frame that exceeds the agent server's 64KiB text-frame cap, and the server responds by closing the session. The bug is invisible to the all-green suites because no component test mounts the session UI and the Playwright e2e never exercises the audio submit path.

## Strengths

- `drainAgentAudio` / `acknowledgeAudio` use identity-based frame acknowledgment (`components/session/LiveSessionPage.tsx`, `lib/viva-agent-client.ts:920-932`) with an explicit written rationale for why positional counts would race with cancellations; cancellations flush before enqueue and the playback sink drops frames for cancelled responseIds (`lib/viva-audio-playback.ts`). A genuinely careful barge-in pipeline, unit tested.
- Both canvases have disciplined render-loop lifecycles: ~32fps rAF throttle, pause on `document.hidden`, debounced ResizeObserver rebuild, DPR-aware sizing, a synchronous first frame, a single static frame under `prefers-reduced-motion`, and complete cleanup on unmount (`VoiceTraceCanvas.tsx`, `MuseGlyphCanvas.tsx`). Voice amplitude flows through mutable refs into the rAF loop, never React state.
- Turn-taking legibility is well executed: concise state-derived `aria-live` announcers deliberately scoped so screen readers are not re-read the whole panel (`MarginaliaPanel.tsx:112-114`, `marginaliaAnnouncement` at 443-456), a dedicated sr-only live region for new questions separate from the heading (`QuestionStage.tsx:55-57`, tested in `QuestionStage.test.tsx`), and focus management into the source folio and text-answer form.
- Honest state copy: pending/terminal question gating ensures a connecting or closed session never renders "Listening…" (`QuestionStage.tsx:31-35`, `session-data.ts:40-45`), with direct tests for both cases.
- `LandingEntry.test.tsx` exercises the real `app/page` server component with env and fetch stubbing, asserting allowlist filtering and that session/control tokens are redacted from the browser snapshot — real behavior, not mocks of mocks.
- Async mic startup is race-hardened: a generation counter (`micStartGenerationRef`) plus `textAnswerModeRef` checks abort stale `getUserMedia` results after mode switches or re-entries (`LiveSessionPage.tsx:384-451`).

## Findings

### Critical

**1. Live-mode spoken answers exceed the 64KiB protocol frame cap after ~1s of audio and terminate the session**

`apps/web/components/session/LiveSessionPage.tsx:484-515` (with `apps/web/lib/viva-agent-client.ts:917-918`)

**What**: When the live runtime is selectable (`shouldUseLiveMicAudioTransport` true), `onFrame` (lines 416-426) buffers every PCM16 chunk into `capturedTurnPcm16Ref` with no size cap, and `submitSpokenTurn` merges the whole turn with `pcm16ChunksToBase64` and sends it as ONE JSON text frame via `agent.sendAudio` — `sendSubmissionFrame` sends a single frame and refuses a second while one is pending (`viva-agent-client.ts:826`), and `audioClientFrame` (`packages/core/src/agent-contract.ts:247-257`) has no chunking. At the protocol's 24kHz pcm_s16le (`VIVA_VOICE_SAMPLE_RATE_HZ = 24_000`, `packages/core/src/agent-contract.ts:2`), raw audio accrues at 48,000 bytes/s, so base64 grows at 64,000 chars/s — but the server caps text frames at `VIVA_VOICE_MAX_TEXT_FRAME_BYTES = 64 * 1024` (a non-configurable const, `agent/crates/agent-service/src/protocol.rs:12`, enforced at `ws.rs:2908`), and a frame error sends an error frame and then closes the socket (`ws.rs:714-718`).

**Why it matters**: Any spoken answer longer than roughly one second — essentially every real answer in an oral exam — produces an oversized frame, the server closes the WebSocket, and the student loses the live session mid-turn. The default synthetic demo is unaffected (the audio transport gate requires `ready.brain.live_runtime && selectable`), which is why the green suites never see it; the Playwright e2e (`scripts/e2e-browser.mjs`) grants mic permission but never exercises the spoken-audio submit path.

**Fix**: Stream audio incrementally during capture (send each captured frame as its own audio frame while the turn is open), or chunk the buffered turn into pieces that serialize under the cap at submit and let the controller send a sequence (relaxing `sendSubmissionFrame`'s single-pending-frame rule for audio). Mirror `VIVA_VOICE_MAX_TEXT_FRAME_BYTES` as a constant in `@viva/core` and add a web-side contract test asserting a maximum-length spoken turn serializes under it.

### Important

**1. "Challenge citation" sends a magic string the agent grades as a student answer**

`apps/web/components/session/LiveSessionPage.tsx:531-537`

**What**: `challengeSource` sends the literal text `"(challenge citation)"` through `agentRef.current.sendText` — a plain protocol Text frame. No code anywhere in agent/, packages/, or apps/web handles this string (verified by repo-wide grep: its only occurrences are the sender and UI labels). On the server, `ClientFrame::Text` becomes `BrainInput::Text`, and the synthetic brain unconditionally spawns a graded study-answer sequence for every text input (`agent/crates/agent-adapters/src/synthetic.rs:186-199`); the live brain forwards it to Gemini as the student's utterance. The `challenge_correction` tool (`agent-domain/src/tools.rs:103`) is an LLM-proposed tool, not reachable from a client text frame.

**Why it matters**: The brain receives "(challenge citation)" as the student's answer to the open question and evaluates it: the student gets a garbage grading turn recorded against the current concept (polluting the mastery/FSRS record) and the examiner's spoken response addresses a nonsense answer. The UI presents this as a first-class action (the SourceFolio "Challenge citation" button).

**Fix**: Add a first-class challenge intent to the protocol (a typed client frame or text-intent envelope) that routes to the `challenge_correction` flow without being graded as an answer, or hide the challenge button until the protocol supports it. At minimum, stop submitting the placeholder through the graded-answer channel.

**2. Route identity is read (and the URL mutated) inside a useState initializer — render-phase side effect and conditional hydration mismatch**

`apps/web/components/session/LiveSessionPage.tsx:78, 1143-1169`

**What**: `readBrowserSessionRouteIdentity` runs as the `useState` initializer: during render it reads `window.location` and calls `canonicalizeSessionBrowserUrl`, which performs `history.replaceState` stripping the session token from search and hash (`lib/viva-session-entry.ts:83-93, 123-132`) — a side effect in render. StrictMode deliberately double-invokes this initializer, and the second invocation reads the already-mutated URL (token gone); which result React keeps is an unguaranteed implementation detail. Separately, the server prerender of `/session` (a plain client-component import in `app/session/page.tsx`, no ssr:false) computes identity from env fallbacks (`sessionRouteIdentityFromSearch("")` plus `NEXT_PUBLIC_VIVA_VOICE_SESSION_TOKEN`) while the client initializer computes it from the URL. Readiness-derived markup — `sessionContextLabel` "Trusted server set" vs "Local demo set" (`LiveSessionPage.tsx:806-809`), driven synchronously by `agentStudySetReadiness` (`packages/core/src/index.ts:570`) over the route-derived study set — diverges whenever a bootstrap URL's `study_set_id` or readiness reason differs from the build-time seed/env configuration.

**Why it matters**: In hosted configurations where the allowlisted study set differs from the seeded trusted id, every session entry via a bootstrap link hydrates mismatched HTML: React 19 logs a hydration failure and discards the server HTML for a full client re-render (console noise, flicker, and a trap for future error monitoring). The render-phase `replaceState` also relies on an unguaranteed React behavior to avoid losing the token in dev.

**Fix**: Read route identity and canonicalize the URL in a mount effect (or `useSyncExternalStore` with a server snapshot matching the env fallback), rendering a neutral connecting state until identity resolves. Keep the token-stripping `replaceState` in the effect, before connect.

**3. Single-click permanent deletion with no confirmation for study sets and session recaps**

`apps/web/components/landing/LibraryStatusPanel.tsx:74-89, 261-269`

**What**: "Delete source" and "Delete recap" buttons call `deleteVivaStudySet` / `deleteVivaSessionHistory` immediately on click — no confirmation dialog, no undo, no two-step affordance (no `confirm` anywhere in the landing components). The delete button sits in the same action row directly beside "Start" and "Resume".

**Why it matters**: These are server-side destructive operations on the learner's uploaded course material and durable session history (docs/data-governance.md emphasizes deletion is real). One misclick next to "Resume" permanently destroys a study set and its mastery history with only a transient "Delete source complete." status line.

**Fix**: Add a confirmation step (inline confirm state on the button, or a dialog naming the study set) before invoking the delete APIs, or implement soft-delete/undo server-side and surface an "Undo" in the status line.

**4. The component test suite never mounts the session UI, and no test anywhere exercises the live audio submit path**

`apps/web/components/session/LiveSessionPage.test.tsx:1-33`

**What**: `LiveSessionPage.test.tsx` imports only the exported pure helpers; the component itself — 800+ lines of effect orchestration (deferred connect, pointerdown-once listener, mic generation races, audio drain effect, consent gating) — is never rendered, and every other component test (`LiveSessionShell.test.tsx`, `QuestionStage.test.tsx`, `LandingHero.test.tsx`, `SessionBottomControls.test.tsx`, `LandingEntry.test.tsx`) uses `renderToStaticMarkup`, so no effect, event handler, or focus-management path executes in the bun suite. A Playwright e2e does mount the real page in a browser (`scripts/e2e-browser.mjs`: connect, end-session, recap, second-tab session cap, bfcache URL-token hygiene), which narrows the gap — but it runs the synthetic path only and never injects mic audio or exercises `sendAudio`, barge-in acknowledgment, or the mic-race seams.

**Why it matters**: The helpers are well tested, but the riskiest code in this area is the effect wiring that composes them — the critical finding above lives entirely in composition and is invisible to every existing suite. String-matching static markup also cannot catch focus management (`MarginaliaPanel.tsx:85-91`) or the once-listener lifecycle.

**Fix**: Add a happy-dom/jsdom (bun test supports happy-dom) or Playwright component-test layer that mounts `LiveSessionPage` with a scripted fake controller and asserts: connect fires once after token refresh, spoken-turn submit sends buffered audio under the frame cap, cancellation flips the interrupt nudge, and recap stops capture. Even 5-6 mounted tests would cover the highest-risk seams.

### Minor

**1. `sessionTokenRef` not updated by the mount-time token refresh, diverging from state**

`apps/web/components/session/LiveSessionPage.tsx:175-190`

**What**: The mount refresh effect calls `setSessionToken(refreshedToken)` but never updates `sessionTokenRef.current` (initialized at line 109); only the lifecycle flows (lines 244, 575) update the ref. After the initial refresh, later bfcache/popstate reconnects and `refreshSession` post the original route token to `/api/viva-session/refresh`.

**Why it matters**: It works today only because `handleVivaSessionRefresh` verifies claims statelessly and accepts expired tokens. If token verification ever becomes stateful (revocation on rotation), lifecycle recovery silently breaks. Two sources of truth for one credential is a divergence trap.

**Fix**: Set `sessionTokenRef.current = refreshedToken` inside the mount refresh effect, or derive the ref from a single token store used by both paths.

**2. Session-entry token refresh has no timeout; a hung refresh blocks connect indefinitely**

`apps/web/components/session/LiveSessionPage.tsx:1191-1215`

**What**: `refreshBrowserSessionToken` awaits `fetch('/api/viva-session/refresh')` with no AbortController/timeout, and the connect effect (line 197) is gated on `routeSessionTokenRefreshReady`, which only becomes true when this promise settles. A stalled connection never rejects.

**Why it matters**: If the refresh proxy stalls, the session page sits in the connecting state forever with no retry affordance — the student's only recovery is a manual reload.

**Fix**: Wrap the fetch with `AbortSignal.timeout(~5-8s)`; on timeout, fall back to the original route token (the existing catch already does this) so connect proceeds.

**3. Global error boundary renders raw `error.message` and never reports the error**

`apps/web/app/error.tsx:12`

**What**: `AppError` prints `error.message` directly into the page, ignores `error.digest`, and has no logging/reporting side effect.

**Why it matters**: Client-side error messages can leak internal details (URLs, state names) to end users, and without the digest or a report hook, production errors on the session page are hard to correlate.

**Fix**: Show calm generic copy plus the digest when present ("Reference: {digest}"), and log the error in a `useEffect` for observability.

**4. Recap due dates formatted with UTC getters, showing the wrong local day for many users**

`apps/web/components/session/MarginaliaPanel.tsx:528-530`

**What**: `formatRecapDueDate` uses `getUTCMonth`/`getUTCDate`/`getUTCFullYear` on the FSRS `dueAt` Date.

**Why it matters**: For learners west of UTC, a review due tomorrow evening local time renders as the day after tomorrow (and vice versa east of UTC) — the review plan's dates visibly disagree with the interval labels beside them.

**Fix**: Format with local getters (or `Intl.DateTimeFormat`), keeping UTC only if the scheduling contract is explicitly calendar-UTC — in which case label it.

**5. Typed answers reach live providers before the recording disclosure is acknowledged**

`apps/web/components/session/LiveSessionShell.tsx:117-133`

**What**: The consent banner is a non-blocking sibling above the stage and gates only microphone capture (`canStartMicrophoneCapture`). The "Write answer" path is active whenever the socket is ready, so a student can submit a written answer to Cartesia/Gemini before acknowledging — yet the disclosure copy states acknowledgment covers "answers" being sent to those providers.

**Why it matters**: docs/data-governance.md only mandates the disclosure before microphone capture (lines 11-12, 27-28), so this is not a policy violation, but the on-screen copy promises more than the gate enforces — a copy/behavior mismatch on a privacy-sensitive surface prepared for public release.

**Fix**: Either gate `sendText` on acknowledgment in live mode, or narrow the disclosure copy to microphone audio, matching the documented contract.

**6. The landing command input's text is silently discarded**

`apps/web/components/landing/LandingEntry.tsx:31-33`

**What**: `enterSession()` takes no arguments: whatever the student types into "Where should Viva begin?" (and whichever suggestion chip they tap) navigates to the identical `/session` target with nothing carried over, despite `onSubmit`/`onSuggestion` plumbing an `intent` string all the way here.

**Why it matters**: A prominent, keyboard-focusable input with zero effect on the resulting session is misleading UX and dead data flow.

**Fix**: Carry the intent into the session route (e.g., an intent query param the session page forwards as the initial goal), or replace the free-text input with an explicit "Begin session" affordance until intent is honored.

**7. Per-frame label planning allocates and re-solves layout 32 times per second**

`apps/web/components/session/VoiceTraceCanvas.tsx:626-643`

**What**: Every `draw()` call rebuilds `nodeDrawState` and runs `planVoiceTraceConceptLabels` — candidate-row generation, overlap scoring, and per-label allocation — even though anchors only wobble a few pixels and the plan is stable between state/resize changes. Because the wobble is applied to the points before planning, a label can also flip between candidate lanes on wobble boundaries.

**Why it matters**: At 32fps with 7+ concepts this is steady GC churn on a page already running two canvases, mic capture, and audio playback; on low-end laptops it costs headroom the voice pipeline needs, and the lane flips cause occasional label jitter.

**Fix**: Compute label plans once per (conceptNodes, canvas size, fontScale) change, cache them outside the rAF loop, and apply the per-frame wobble as an offset to the cached positions.

## Verification notes

No findings were refuted or downgraded; all twelve survived adversarial verification against the source.

- The critical audio-frame finding was verified end to end: client-side buffering and single-frame send (`LiveSessionPage.tsx:416-426, 484-515`; `viva-agent-client.ts:806-832, 917-918`; `agent-contract.ts:247-257`), the 24kHz rate constant, the non-configurable 64KiB server cap (`protocol.rs:12`, `ws.rs:2908`), and the error-then-close path (`ws.rs:714-718`).
- The challenge-string finding was verified by repo-wide grep (no handler anywhere) plus the synthetic brain's unconditional grade-every-text-input behavior (`synthetic.rs:186-199`).
- The test-coverage finding (Important 4) was narrowed during verification: the first pass claimed reconnect/bfcache flows "can regress without any test failing," but `scripts/e2e-browser.mjs` does mount the real page in Playwright and audits connect, recap, and bfcache URL-token hygiene. The corrected claim — no mounted component tests, and zero coverage anywhere of the live audio submit and barge-in seams — stands, and severity was kept at important because that uncovered seam is exactly where the critical bug lives.

## Recommendations

1. Fix the live audio turn transport first: stream or chunk mic audio within the protocol frame caps, mirror `VIVA_VOICE_MAX_TEXT_FRAME_BYTES` into `@viva/core`, and add a web-side contract test that a maximum-length spoken turn serializes under the cap.
2. Give "Challenge citation" a real protocol path (or hide it): a typed client intent that reaches the `challenge_correction` flow without being graded as an answer.
3. Move route-identity reading and URL canonicalization out of the `useState` initializer into a mount effect (or `useSyncExternalStore`) to make `/session` hydration-safe and render-pure.
4. Add a mounted-component test layer (happy-dom or Playwright CT) covering LiveSessionPage's effect orchestration: deferred connect, spoken-turn submit, barge-in acknowledgment, recap teardown, and bfcache reconnect — complementing, not duplicating, the existing synthetic-path e2e.
5. Add confirmation or undo to the library's destructive delete actions.
6. Add `AbortSignal.timeout` to session-entry fetches (token refresh, session start) so a stalled proxy cannot block session entry indefinitely.
7. Reconcile the recording-disclosure copy with what the consent gate actually enforces (mic-only today), in whichever direction data governance prefers.
8. Cache VoiceTraceCanvas label plans between state/resize changes instead of re-solving layout every animation frame.

## Assessment

**Verdict: sound-with-fixes** (unchanged from the first-pass reviewer; verification confirmed all findings, narrowing one).

The area shows unusually careful React and canvas engineering — disciplined render-loop lifecycles, ref-based audio levels, identity-based audio acknowledgment, race-hardened mic startup, and genuinely thoughtful voice-first accessibility — and the synthetic demo path is solid, with real e2e coverage. But one confirmed critical cross-layer contract bug breaks the flagship live path (spoken turns exceed the server's 64KiB frame cap after about one second of speech and the server closes the session), and it is invisible to every existing suite because nothing mounts the session component or exercises live audio. Together with the magic-string challenge action, the hydration-unsafe route-identity initializer, and unconfirmed destructive deletes, the area needs a focused round of fixes before the live voice experience is production-ready.
